# 사용자 화면 재설계 — 합의된 설계

2026-09-01 논의. **아직 구현하지 않았다.** 착수 전에 이 문서를 다시 읽을 것.

---

## 왜 고치나

현탁액을 고르면 ② 단계가 매운소스 전용처럼 보인다. 원인은 두 겹이다.

**제형 파일에 제품이 박혀 있다.** `layerM_cards_suspension.yaml` 의 meta 가
그대로 이렇게 적혀 있다:
       
    Suspension (solid-in-liquid dispersion) - default product: fermented hot sauce

쌀음료·커피우유는 제품 단위 카드 파일(F7 패턴)로 분리돼 있는데, 현탁액은
발효 핫소스가 제형 파일 안으로 들어갔다.

**그런데 카드는 이미 둘을 구분하고 있다.** `default_goal` 이 그 표시다.

| 제형 | `target` (제품 성격) | `maintain`/`minimize` (공통) |
|---|---|---|
| 현탁액 | 매운맛, 매운맛 여운, 감칠맛, 건고추 향, 장 발효 향 | 짠맛, 신맛, 단맛, 걸쭉함, 꺼끌거림 |
| 커피우유 | 쓴맛, 커피 향 | 단맛, 신맛, 바디감, 탁함, 우유 향 |
| O/W 소스 | — | 짠맛, 신맛, 단맛, 감칠맛, 걸쭉함, 크리미함, 코팅성 |

게다가 문제의 두 축에는 이런 메모가 붙어 있다:

    L.ar.dried_red_chili — "User-selectable at project onboarding;
                            default for fermented hot sauce. Swappable."

온톨로지 저자가 **"프로젝트 시작 때 사용자가 고르고 바꿀 수 있는 축"** 이라고
이미 적어 뒀는데 UI 가 10개를 평평하게 늘어놓았다. 새 온톨로지 작업이 아니라
이미 있는 구분을 읽는 일이다.

## 정한 것

| 주제 | 결정 |
|---|---|
| ① 입구 | 서술형 한 문장 + 읽어낸 것을 칩으로 확인 |
| 문장 해석 | 모델(Claude API), 고를 수 있는 값을 온톨로지 ID 로 제한 |
| 제품 사전 | 초안 30개 내가 작성 → 검토표로 판정 |
| 미등록 재료 | 기능군만 받고 즉시 사용(잠정 등록), 검증은 뒤따라감 |
| ③ 재료 | 키 재료만 받고 나머지는 시스템이 제안 |

## 측정: 지금 어휘로 서술형이 되나

한글 이름만으로 부분문자열 매칭을 해 봤다.

| 입력 | 잡힌 것 | 놓친 것 |
|---|---|---|
| "고추장 베이스로 **매운 소스**" | 고추장 | 매운, **소스(제형)** |
| "쌀로 만든 **부드럽고 덜 단** 음료" | 없음 | 전부 |
| "**마요네즈**처럼 **꾸덕한** 드레싱" | 없음 | 전부 |
| "토마토 **살사**" | 토마토 페이스트 | 살사(제형) |
| "**저당** 아이스크림, 얼음 씹히지 않게" | 얼음 씹힘 | 저당 |

명사는 잡히나 **제형과 정도 표현은 하나도 안 잡힌다.** "아이스크림" 이
"크림 향" 에 걸리는 부분문자열 오탐도 나왔다.

빠진 층이 셋이다 — 제품 사전, 표현 사전, 형태소 처리. 이 중 **제품 사전만
표로 만들고 나머지는 모델에 맡긴다**. 제품→제형 매핑은 도메인 지식이고 틀리면
사용자가 잘못된 축 묶음으로 끌려가 서술형이 가장 비싸게 실패한다. 정도 표현은
무한하고, 칩으로 확인받으므로 오류가 싸게 끝난다.

## 흐름

```
① "어떤 걸 만들고 싶으세요?"   [한 문장]
     → 읽어낸 것을 칩으로 보여주고 고치게 한다
         [제형: 현탁액 ▾]
         [성격: 매운맛 ✕   건고추 향 ✕   + 추가]
         [재료: 고추장 ✕]
         [목표: 단맛 ↓]
     → 못 읽으면 그냥 "고르기로 시작" 으로 전환 (서술형은 입구지 관문이 아니다)

② 기준 제품 + 공통 축 조정
     공통 축(maintain·minimize·increase·decrease)만 "기준보다 더/덜"
     성격 축(target)은 ① 에서 이미 골랐으므로 "얼마나 강하게" 만

③ 키 재료
     검색으로 약속된 재료만 넣는다 (① 에서 읽어낸 재료가 씨앗)
     없으면 기능군만 받아 잠정 등록 → 즉시 사용
     시스템이 빈 곳을 이유와 함께 제안 → 각각 수락/거절

④ 배합 제안
```

세 결정이 서로 맞물린다. ① 이 읽어낸 재료가 ③ 의 씨앗이 되고, ③ 에서 없는
재료는 기능군만으로 즉시 살아난다.

## 제품 사전

**위치** `ontology_v2/layers/layerS3_products.yaml` (새 파일). 앱이 직접 읽는다 —
정본 로더의 glob(`layerC2_*`, `layerM_cards_*`, `layerL_*`, `layerS2_*`)에 걸리지
않으므로 로더는 건드리지 않는다.

**성질** 새로운 주장을 담지 않는다. 모든 값이 이미 있는 profile id 와 term id 를
가리키는 **색인**이다. 그래서 불변식과 충돌하지 않는다.

```yaml
- id: PROD.hot_sauce_fermented
  ko: 발효 핫소스
  aliases: [핫소스, 매운소스, 고추장소스]
  profile: suspension
  identity_axes: [L.ch.pungent_hot, L.ch.heat_linger,
                  L.ar.dried_red_chili, L.ar.soy_fermented_jang]
  typical_ingredients: [ING.gochugaru_coarse, ING.gochujang, ING.vinegar_brewed]
```

**덤으로 뿌리가 뽑힌다.** 지금 현탁액 카드 파일이 하드코딩한 "default product:
fermented hot sauce" 가 이 항목으로 옮겨 간다. 제형은 다시 일반적인 것이 되고
제품이 정체성을 진다.

**작업 방식** 30개 내외 초안 → `draft_review.xlsx` 방식 검토표 → 판정 반영.
특히 확인받아야 할 것: 마요네즈·드레싱이 `sauce_ow` 인지, 살사·핫소스가
`suspension` 인지.

## 문장 해석 계약

**모델** `claude-sonnet-5`. 제약된 추출 작업이라 빠르고 싸다. temperature 0
— 같은 문장에 같은 답이 나와야 한다.

**입력** 사용자 문장 + 고를 수 있는 값 목록
(제품 사전 항목, 제형, 정체성 축 후보, 재료 118종 한글명)

**출력** 구조화된 JSON

```
profile          제형 id (또는 후보 여럿)
identity_axes[]  L.* term id
ingredients[]    ING.* id
goals[]          {term, direction}   "덜 달게" -> {L.ta.sweet, decrease}
unresolved[]     목록에 없어서 못 맞춘 말 그대로
```

**제약** 모든 값은 제공된 목록에서만 고른다. 없는 재료를 지어낼 수 없다.
못 맞춘 말은 `unresolved` 로 넘겨 사용자에게 그대로 보여 준다 — 미등록 재료
등록의 입구가 된다.

**방어선** 칩 확인. 모델이 틀려도 사용자가 보고 고친다.

**폴백** API 키가 없거나 호출이 실패하면 제품 사전 + 한글 부분문자열로 내려간다.
품질은 떨어지지만 멈추지 않는다. 이때 "아이스크림→크림 향" 류의 오탐을 막을
경계 검사가 필요하다.

## 제형 모호성

"소스" 는 `sauce_ow`(에멀전)와 `suspension`(현탁) 둘 다다. 제품 사전에 있는 말
(마요네즈, 살사)은 사전이 끊는다. 일반어로 말하면 **한 가지만 되묻는다**:

> "기름이 들어가나요, 아니면 건더기가 씹히나요?"

이 한 질문이 O/W 와 현탁을 정확히 가른다. 두 개 이상 묻지 않는다.

## 미등록 재료 잠정 등록

EFFECT 헤더가 이 길을 이미 열어 뒀다:

    2-TIER: generic effects live on FUNCTION TAGS
            (prior backbone + enables new-ingredient generalization via descriptors)

새 재료에 필요한 것은 **이름 + 기능군** 뿐이다. 그 순간 태그의 사전 효과를
물려받아 모형에 들어간다. 전문가 검증은 override 를 붙이는 일이지 사용자를
막을 이유가 아니다.

**파일** `layerC2_ext_provisional.yaml` — append-only(불변식 3)

```yaml
- id: ING.<slug>
  ko: <사용자가 적은 이름>
  function_tags: [FT.*]        # 사용자가 고른 기능군 (한글 이름 24개)
  status: provisional
  confidence: low
  added_at: <날짜>
  review: pending
```

**화면** 제안 결과에 "아직 검증 전인 재료" 로 표시. 전문가 화면에 검토 대기열
(기존 `review_drafts.py` 패턴 재사용).

## 키 재료 + 빈 곳 제안

부품은 이미 있다 — `default_palette()` 의 축별 대표 선택과 STRUCTURE 의
`required_functions`.

사용자가 댄 재료 집합을 K 라 할 때 빈 곳은 둘이다.

1. **제형이 요구하는 기능군 중 K 가 못 채운 것**
   → "O/W 소스인데 유화제가 없습니다 → 난황"
2. **core 축 중 K 로 못 움직이는 것**
   → "걸쭉함을 조절할 재료가 없습니다 → 잔탄검"

각각 이유와 함께 제안하고 수락/거절을 받는다. 기능군 아코디언은 접어서 남긴다 —
재료를 잘 아는 사람이 직접 훑을 길.

## 착수 순서

1. **제품 사전 초안 30개 + 검토표** — 다른 모든 것의 전제
2. **① 서술형 + 칩 확인** (모델 경로 + 폴백)
3. **③ 키 재료 + 검색 + 빈 곳 제안**
4. **미등록 재료 잠정 등록**

## 아직 안 정한 것

**±3 척도의 의미** — 점수 체계 자체는 좋으나 ±3 이 관능적으로 어느 정도 차이인지
사용자에게 설명이 필요하다. 카드의 `ko.anchors` 가 "기준보다 뚜렷하게 더 달다"
같은 문장을 갖고 있으나 그것이 얼마만큼인지는 말해 주지 않는다.

**DoE / 실험 횟수** — 한 번의 제안으로 끝나지 않는다는 것을 인지시켜야 한다.
수정 제안을 어떤 식으로 낼지, 원하는 정밀도에 따라 몇 회를 제안할지.
계산 근거는 이미 있다: 자유변수 q = p−1, warmloop 의 `eff_directions`
(쌀음료는 15개 중 11개 방향만 탐색됨), 카드 reliability→σ(0.5/1.0/1.8),
스펙 5.7 의 5~20회 지침.

**의존성** 모델 경로를 쓰려면 Anthropic API 키가 이 환경에 있어야 한다. 확인 필요.
