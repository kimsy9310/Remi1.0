## 2. 상호작용 알고리즘

단계마다 이름을 붙인다. `[API]` 표시가 있는 곳에서만 모델을 부른다.

행위자 표기: **[사]** 사용자가 고른다 · **[R]** Remi 가 규칙·계산으로 정한다 ·
**[AI]** 모델을 부른다 · **[전]** 전문가가 나중에 검토한다.

### Phase A — 규정 (FRAME) : 무엇을 만드는가

| 단계 | 이름 | 누가 | 하는 일 | 고르는 것 / 넣는 것 |
|---|---|---|---|---|
| A1 | `INTAKE` | 사 | 한 문장을 받는다 | 자유 문장, 또는 "고르기로 시작"(문장 없이 진행) |
| A2 | `PARSE` | **AI ★** | 문장 → 온톨로지 ID | 넣는 것: 문장 + 후보 목록(재료 118·정체성 축 134·기능군 24·제품 사전 30)<br>받는 것: 제형 / 정체성 축[] / 재료[] / 목표[] / 못 읽은 말[] |
| A3 | `DISAMBIGUATE` | R → 사 | 제형이 안 좁혀지면 **한 번만** 되묻는다 | 조건: 후보 2개 이상일 때만<br>선택지: 기름 → `sauce_ow` / 건더기 → `suspension` |
| A4 | `CONFIRM` | 사 | 읽어낸 것을 칩으로 확인·수정 | 제형 바꾸기 · **정체성 축 빼기/더하기**(렉시콘 134개) · 재료 빼기/더하기 · 목표 방향 |

**→ Output 1 (제품 규정).** 4.7 절 참조.

### Phase B — 목표 (TARGET) : 어떻게 만들 것인가

| 단계 | 이름 | 누가 | 하는 일 | 고르는 것 / 넣는 것 |
|---|---|---|---|---|
| B1 | `SCOPE` | R ★핵심 | 물어볼 축 조합을 정한다 | 자동. 3 절의 규칙표대로 |
| B2 | `ORIGIN` | 사 | ±3 의 0 점을 정한다 | `A2` 가 원점을 못 찾았을 때만 뜬다.<br>묻는 말: **"비교하며 맛볼 수 있는 제품이 손에 있나요?"**<br>없으면 → 첫 시제품이 원점 |
| B3 | `GOALSET` | 사 | 목표 입력 | 바꿀 축을 **칩으로 먼저 고르고**, 고른 것만 −2…+2<br>정체성 축은 강도만 · "상관없음" |

**→ Output 2 (목표 명세).** 이 프로젝트의 깃발이다 — 4.7 절 참조.
`C` 는 이것을 입력으로 받는다.

### Phase C — 재료와 공정 (RESOURCES)

| 단계 | 이름 | 누가 | 하는 일 | 고르는 것 / 넣는 것 |
|---|---|---|---|---|
| **C0** | **`PROCESS`** | 사 | 규모와 공정을 선언한다 | 규모(주방/파일럿/공장) + 제형이 정하는 조작 **1~5칸**.<br>무엇을 묻는지는 온톨로지가 계산한다 — 아이스크림 5칸, 쌀음료 1칸 |
| C1 | `SEED` | R | A4 의 재료를 초기 집합으로 | 자동 |
| C2 | `SEARCH` | 사 | 검색으로 더하고 뺀다 | 한글명·기능군·담당축으로 검색 → 선택<br>**반드시 쓸 재료 / 절대 안 쓸 재료** 지정 |
| C3 | `ENROLL` | 사 → 전 | 없는 재료를 즉시 쓰게 한다 | 사용자: **이름 + 기능군 하나**(24개 중)<br>전문가: 나중에 override 검토 |
| C4 | `GAPFILL` | R | 빈 곳 탐지 | 자동. ① 제형 필수 기능군 미충족 ② core 축을 못 움직임<br>③ **공정** — 재료로는 못 가는 축이 있다(꺼끌거림은 재료 액추에이터가 없다) |
| C5 | `ACCEPT` | 사 | 제안 처리 | 제안마다 수락 / 거절 — 거절해도 진행 |

| 단계 | 이름 | 누가 | 하는 일 | 고르는 것 / 넣는 것 |
|---|---|---|---|---|
| D0 | `FEASIBILITY` | R → 사 | **갈 수 있는지 판정한다** | 자동 판정 + 상충 보고 + **장비로 닿는지**.<br>못 가면 **되돌아갈 곳 네 갈래** — `A4` 축 / `B3` 목표 / **`C0` 공정** / `C2` 재료 |

## 3. B1 `SCOPE` — 질문 선택 정책

**질문 은행은 이미 있다.** M 카드 70장(core 38장)이 그것이고, 새로 만들 것이
없다. 없는 것은 **어떤 조합을 물을지 정하는 규칙**이다. 그게 B1 이다.

| 카드 | 판정 근거 | ② 에서 |
|---|---|---|
| `tier: monitored` | tier | 안 묻는다 (이미 그렇다) |
| `evidence_required: sample_aged` | 5.8 격리 | 안 묻는다 (이미 그렇다) |
| core + `default_goal: target` | default_goal | **Phase A 에서 정한다.** ② 는 "얼마나 강하게" 만 |
| core + `default_goal: minimize` | default_goal | 안 묻는다. 기본 최소화, "신경 쓰이는 것 있나요" 로 접어 둔다 |
| core + `maintain`/`increase`/`decrease` | default_goal | 묻는다. 단 **먼저 칩으로 "바꾸고 싶은 것만" 고르게 하고, 고른 것만 슬라이더** |

## 4. A2 `PARSE` — 유일한 API 지점

### 왜 여기 하나뿐인가

자연어가 시스템에 들어오는 곳이 A1 하나다. 그 뒤는 전부 온톨로지 조회와 수치
계산이다. **A3 는 규칙, C4 는 집합 연산, D3 는 템플릿, D1·D2 는 순수 계산.**
C3 은 사용자가 기능군 24개 중 고르면 API 가 필요 없다 — 추정을 맡길 때만 선택.

세션당 API 호출 **1회**가 설계 목표다.

### 계약

입력 = 사용자 문장 + 고를 수 있는 값 목록
출력 = 구조화된 JSON (`output_config.format` 으로 스키마 강제)

```
profile          제형 id, 또는 후보 여럿 (A3 로 넘어감)
identity_axes[]  L.* term id
ingredients[]    ING.* id
goals[]          {term, direction}      "덜 달게" -> {L.ta.sweet, decrease}
unresolved[]     목록에 없어 못 맞춘 말 그대로
```

**제약** 모든 값은 제공된 목록에서만 고른다. 없는 재료를 지어낼 수 없다.
못 맞춘 말은 `unresolved` 로 넘겨 그대로 보여 준다 — C3 `ENROLL` 의 입구다.

**방어선** A4 `CONFIRM` 의 칩. 모델이 틀려도 사용자가 보고 고친다.

### 페이로드 (실측)

| 넣을 것 | 건수 | 글자 |
|---|---|---|
| 재료 한글명 | 118 | 2,934 |
| 정체성 축 후보 (L.ar + L.ch) | 134 | 2,800 |
| 기능군 | 24 | 542 |
| 제품 사전 | ~30 | ~600 |
| 시스템 프롬프트 + 스키마 | — | ~1,500 |

합계 약 8,400자 ≈ **3,000~5,000 입력 토큰**. 출력 200~250 토큰.

### 비용 설계

호출마다 **똑같은 앞부분**(목록 + 스키마)이 오고 뒤에만 사용자 문장이 붙는다.
캐싱이 정확히 이 모양을 위한 것이다 — 안정된 것을 앞에, 변하는 것을 뒤에 두고
마지막 안정 블록에 `cache_control` 을 건다. 캐시 읽기는 입력가의 약 0.1배다.

세션당 1회 호출 기준 대략:

| 모델 | 입력가/출력가 (1M) | 캐시 미스 | 캐시 히트 |
|---|---|---|---|
| Opus 5 | $5 / $25 | ~$0.026 | ~$0.008 |
| Sonnet 5 | $2 / $10 | ~$0.011 | ~$0.003 |
| Haiku 4.5 | $1 / $5 | ~$0.005 | ~$0.002 |

**기본은 Opus 5 로 둔다.** 모델을 낮추는 것은 품질을 파는 결정이라 내가 임의로
할 일이 아니다. 구조화 추출은 하위 모델도 잘하는 작업이니, 실제 문장으로
품질을 재 보고 나서 정하면 된다.

핵심은 모델 선택이 아니라 **호출 횟수 규율**이다. 단계마다 부르기 시작하면
5~10배가 되고, 그건 모델을 낮춰서 만회할 수 없다.

지킬 것:

1. **한 번에 전부 추출** — 제형·축·재료·목표를 나눠 부르지 않는다
2. **목록만 넣고 설명은 빼기** — `ING.x|한글명` 한 줄씩. 정의·효과는 안 보낸다
3. **캐싱** — 목록·스키마를 앞에, 사용자 문장을 뒤에
4. **사전 히트면 호출 자체를 건너뛴다** — "마요네즈 만들래" 는 제품 사전에서
   바로 걸린다. API 를 안 부르는 것이 가장 싼 호출이다
5. **재파싱 금지** — 칩 수정은 UI 조작이지 새 호출이 아니다

### 폴백

API 키가 없거나 호출이 실패하면 제품 사전 + 한글 부분문자열로 내려간다.
품질은 떨어지지만 멈추지 않는다. 이때 오탐 방어가 필요하다 — 측정에서
"아이스크림" 이 "크림 향" 에 걸렸다.

### 지금 어휘로 폴백이 어디까지 되나 (실측)

| 입력 | 잡힌 것 | 놓친 것 |
|---|---|---|
| "고추장 베이스로 **매운 소스**" | 고추장 | 매운, **소스(제형)** |
| "쌀로 만든 **부드럽고 덜 단** 음료" | 없음 | 전부 |
| "**마요네즈**처럼 **꾸덕한** 드레싱" | 없음 | 전부 |
| "토마토 **살사**" | 토마토 페이스트 | 살사(제형) |
| "**저당** 아이스크림, 얼음 씹히지 않게" | 얼음 씹힘 | 저당 |

명사는 잡히나 제형과 정도 표현은 하나도 안 잡힌다. 그래서 제품 사전이 필요하다.

## 4.5 벤치마크 — 하나가 아니라 세 역할

`A` 와 `B` 에서 같은 말이 다른 뜻으로 쓰이고 있었다. 사용자가
"시판 스리라차 **같은 맛**인데 덜 맵고 마늘 향이 강한 소스" 라고 하면
스리라차 같은 *맛*을 원하는 것이지 스리라차 같은 *제형*을 원한다는 보장이 없다.

| 역할 | 필요한 것 | 언제 | 정하는 것 | **못** 정하는 것 |
|---|---|---|---|---|
| 맛 지향점 | 이름만 | `A2` 이전 | **어떤 축을 켤 것인가** | 그 축의 목표값 |
| 제형 원형 | 이름만 | `A2` | 제형, 딸린 카드 묶음 | — |
| 측정 원점 | **손에 든 시료** | `B3`·`E1` | ±3 의 **0점** | — |

### 뭉개면 실제로 깨진다

스리라차(현탁액)와 마요 계열(O/W 소스)의 core 축은 **공통이 5개, 어긋나는 것이
7개**다. 스리라차를 원점으로 삼으면 크리미함·코팅성은 채점할 대상이 없고,
매운맛 여운·꺼끌거림은 목표 제품에 카드가 없다.

### 규칙

> **`A` 의 참조는 `B` 의 원점으로 자동 승격되지 않는다.**

승격 조건 둘 — ① 제형이 같을 것(계산으로 판정) ② 손에 있을 것(사용자에게 묻는
하나뿐인 질문). 흔한 경우("작년 시제품 3번보다 덜 달게")는 셋이 같은 제품이라
자동으로 참이 되고 질문 하나로 끝난다.

### 맛 지향점으로는 목표값을 못 정한다

±3 이 원점 상대이므로, 원점이 첫 시제품이면 "스리라차 같은 맛" 이 그 시제품
대비 몇인지는 정의되지 않는다. 맛 지향점이 할 수 있는 일은 **축을 켜는 것까지**다.
그래서 맛 지향점은 벤치마크가 아니라 `A4 CONFIRM` 의 정체성 축 칩을 채우는
입력으로 흐른다.

### `A2` 계약 수정

`benchmark` 필드 하나를 없애고 역할을 붙인다.

```
references[]: { name, role: flavor | structure | both, in_hand: unknown }
```

`A1` 은 분기를 두지 않는다. 입력칸 안내에 접어 넣는다:

    "어떤 걸 만들고 싶으세요?  비슷한 제품이 있다면 같이 적어 주세요."

`B2` 는 `A2` 가 원점을 못 찾았을 때만 뜨고, 묻는 말이 다르다 —
"벤치마크가 있나요?" 가 아니라 **"비교하며 맛볼 수 있는 제품이 손에 있나요?"**

### 벤치마크가 없으면 첫 시제품이 원점

절대 서술(`B0 Profiling`)로 가지 않는다. 근거: 지금 데이터의 `B00_bench` 행은
`is_benchmark: yes` 와 제형만 있고 **배합이 비어 있어 학습에서 통째로
건너뛰어진다**. 외부 시판품을 원점으로 삼으면 그 행은 모형에 한 건도 기여하지
못한다. 첫 시제품을 원점으로 삼으면 ① 척도의 0 점이 생기고 ② 그 행에 배합이
있으므로 모형이 실제로 배우고 ③ "DoE 는 적을수록 좋다" 와도 맞는다 — 첫 실험
한 판의 임무가 "원점 만들기" 가 된다.

## 4.6 정체성 축은 2~3개 · 제형과 제품을 가른다

**규칙**: 제품을 그 제품이게 하는 축은 보통 2~3개다. 그 이상이면 제품 정의가
흐려진 것이다.

이 규칙을 지금 온톨로지에 대 보면 한 군데만 걸린다.

| 프로파일 | 정체성 축 | 판정 |
|---|---|---|
| 음료 · 아이스크림 · O/W 소스 | 0개 | 제형 파일이 마땅히 있어야 할 모습 |
| 커피우유 · 쌀음료 | 2개 · 1개 | **제품** 단위 파일(F7)이라 정당 |
| **현탁액** | **5개** | 제형 파일인데 제품이 들어앉음 |

### 더 근본적인 문제 — 제형은 물성만 함의한다

`SC.suspension` 의 정의는 "녹지 않는 고체 입자가 연속된 액상에 분산됨" 뿐이다.
무슨 향이 나는지는 함의하지 않는다. 그런데 core 축 10개를 갈라 보면:

| 갈래 | 현탁액 | 있어야 할 곳 |
|---|---|---|
| ① 제형이 함의 (물성·외관) | 2 — 걸쭉함, 꺼끌거림 | 제형 파일 |
| ② 어느 식품에나 (기본맛) | 4 — 짠맛, 신맛, 단맛, 감칠맛 | 제형 파일 (공통 바탕) |
| ③ **제품이 정함 (향·화학감각)** | **4 — 매운맛, 매운맛 여운, 건고추 향, 장 발효 향** | **제품 파일** |

`감칠맛` 도 기본맛인데 `target` 으로 올라가 있고, 카드 메모가 이유를 적어 놨다 —
*"fermented positioning axis for Ranita products"*. 제품 포지셔닝이 기본맛 축을
타고 들어왔다.

### STRUCTURE 는 이미 알고 있었다

`suspension` 의 `relevant_attributes` 에서 두 향 축이 이렇게 달려 있다:

```yaml
- id: L.ar.dried_red_chili     slot: flavor_user_slot_1
- id: L.ar.soy_fermented_jang  slot: flavor_user_slot_2
```

**"사용자가 채울 칸"** 이라는 선언이다. 그런데 기본값이 값처럼 굳어서
`default_goal: target` 으로 박혔다. 칸의 개수는 제형이 정하고 칸의 내용은 제품이
채우는 것이 원래 설계다.

### 고칠 모양

`PROD.hot_sauce_fermented` 가 정체성 축 셋을 진다 — 매운맛 · 건고추 향 ·
장 발효 향. 나머지는 **삭제가 아니라 강등**이다:

| 축 | 조치 |
|---|---|
| 매운맛 여운 | `target` → `maintain` — 매운맛의 성질이지 별개 정체성이 아니다 |
| 감칠맛 | `target` → `maintain` — 장에 딸려 온다 |

강등된 축은 ② 단계 칩에 그대로 남아 조절할 수 있다. 정체성 표식 자격만 잃는다.
그리고 **생고추 핫소스**라면 셋이 `매운맛 + 신선 고추 향 + 신맛` 이 되고 장 발효
향은 아예 빠진다 — 같은 제형, 다른 제품. 카드 메모가 약속한 교체 가능성이다.

### 검사로 박았다

`engine/selfcheck_v2.py` 에 두 건 추가.

- **정체성 축이 프로파일마다 3개 이하** — 현탁액 5개로 실패
- **제형 파일에 제품 고유 축(향·매운맛)이 없다** — 현탁액 4개로 실패

제품 단위 파일 판정은 `meta.product` 유무로 한다(F7 패턴). 앞으로 카드를 고칠
때마다 자동으로 걸린다.

## 4.7 산출물 — Output 1 · 2 · 3

사용자 그림이 `Output 2: User goal` 을 "the key and flag of the project" 라고
짚고 떠 있는 채로 두었다. 이것이 정해지지 않아 `C1` 에 들어오는 화살표가
없었다 — B 와 C 를 잇는 다리가 곧 이 산출물이다.

### Output 1 — 제품 규정 (`A4` 끝)

```
FRAME {
  profile        제형 또는 제품 id
  identity[]     정체성 축 (2~3개)
  references[]   { name, role: flavor|structure|both, in_hand }
  seed_ings[]    문장에서 읽어낸 재료
}
```

### Output 2 — 목표 명세 (`B3` 끝) ★

**이 프로젝트의 깃발이다.** D 가 소비하고, E 가 갱신하고, 전문가가 검토한다.

```
GOAL {
  frame          Output 1

  origin {                        ±3 이 무엇 대비인지
    kind         external | first_prototype
    name         "시판 스리라차" | null
    in_hand      true | false      false 면 external 일 수 없다
  }

  axes[] {
    term         L.*
    role         identity | adjust | defect
    target       float | null       null = 상관없음
    weight       reliability 에서 온다 (σ 의 역수)
    source       user | default
  }

  constraints {
    must_use[]     반드시 쓸 재료
    must_not_use[] 절대 안 쓸 재료
    limits[]       법적·가격 — 지금은 항상 비어 있다 (아래 참조)
  }

  provenance {
    asked[]        실제로 물은 축
    skipped[]      안 물은 축과 그 이유 (monitored / sample_aged / minimize 접힘)
  }
}
```

`provenance` 를 남기는 이유: 나중에 "왜 이 축은 안 물었나" 를 답할 수 있어야
한다. 전문가가 검토할 때 가장 먼저 보는 것이 그것이다.

### Output 3 — 배합 제안 (`D3` 끝)

```
PROPOSAL {
  recipe[]       { ing, pct, delta_from_start }
  predicted[]    { term, target, expected, residual }
  unmet[]        도달 못 한 축과 이유
  provisional[]  잠정 등록 재료가 쓰였으면 여기 — 예측을 덜 믿을 근거
  doe            보류
}
```

### 법적·가격은 아직 못 본다

확인한 사실: 온톨로지에 **가격 필드가 아예 없고**, `limitations` 61건 중
규격으로 태깅된 것은 4건, 기계가 읽을 수 있는 상한은 **3건**뿐이다(자유 서술,
G5). 알레르기만 제대로 있다(56종 + 한국 표기 13종).

그래서 `C4 GAPFILL` 이 "충분하다" 고 말할 때 그것은 **관능적으로 목표에 닿는다**
는 뜻이지 **팔 수 있다** 는 뜻이 아니다. 이 구분을 화면에도 적어야 한다.
규격 레이어는 별도 과제다.

## 4.8 닫은 구멍 — 사용자 그림의 끊긴 곳 7군데

| 끊긴 곳 | 결정 |
|---|---|
| `◇ 벤치마크 온라인 조사` → Yes | **잘라낸다.** 아래 참조 |
| `B1-1 Benchmark analysis` | 위와 함께 삭제 |
| `B1-2 Scope analysis` | **`D0 FEASIBILITY` 로 이름을 바꿔 D 앞에 둔다** |
| `Output 2` 가 떠 있음 | 4.7 절에서 정의. `B3` → `Output 2` → `C1` |
| `C1` 에 들어오는 화살표 없음 | 위와 같이 이어진다 |
| `◇ 진행할까요?` → Yes | **`D0` → `D1` → … → `E`.** 성공 경로가 통째로 없었다 |
| `재료 목록 못 줌` → 이전 DB | **자동으로 닫힌다.** `C2` 는 선택이고, 아무것도 안 고르면 `C4` 가 온톨로지에서 세운 후보로 전부 채운다(`default_palette`) |

### 온라인 벤치마크 조사를 자른 이유

원점은 **손에 든 시료**여야 한다(척도 문서). 시판품의 공개 조성을 찾아와도
우리 축의 관능 점수는 알 수 없고, 결국 맛봐야 한다. 즉 이 호출이 사는 것은
"그 제품의 배합 추정" 뿐인데 — 공개 조성은 부정확하고, 더 나쁜 것은 사용자가
**원점을 얻었다고 착각하게 만든다.** API 지점도 3 → 1 로 돌아온다.

되살릴 여지는 있다. 벤치마크가 손에 있고 조성까지 알면 `x0` 를 그 근처에서
시작할 수 있다. 쓸 일이 생기면 그때 붙인다.

## 4.9 `D0 FEASIBILITY` — 성공 경로와 실패 경로가 갈리는 곳

사용자 그림의 `C3 Analyze ingredients` + `◇ Do you want to proceed?` 가
여기다. 푸는 것은 두 가지다.

**① 도달 가능한가.** 목표를 준 축마다, 고른 재료 중 그 축을 움직이는 것이
있는가. 없으면 그 축은 목표를 줘도 반응하지 않는다.

**② 서로 부딪치는가.** 사용자 노트가 짚은 "counteracting ingredients" 다.
단맛을 올릴 재료가 걸쭉함도 올리는데 걸쭉함을 낮추라고 했다면 둘은 동시에
만족할 수 없다. 계산은 이미 있다 — QP 가 절충안을 내고 잔차가 남는다.
없던 것은 **그 잔차를 사람 말로 돌려주는 일**이다.

    "단맛↑ 과 걸쭉함↓ 은 같은 재료(쌀조청)가 움직여 동시에 만족할 수 없습니다.
     둘 중 무엇을 우선할까요?"

**실패 경로.** 못 간다고 판정되면 어디로 돌아갈지 세 갈래로 제시한다 —
`A4`(정체성 축 고치기) · `B3`(목표 낮추기) · `C2`(재료 더하기). 사용자 그림의
"A3, B1 or C1" 과 같은 뜻이고, 우리 단계 이름으로 옮긴 것이다.

## 4.10 공정 — `C0 PROCESS`

전략과 근거는 [`docs/공정_전략.md`](공정_전략.md) 에 따로 있다. 알고리즘 쪽 요약만
여기 둔다.

**왜 Phase C 인가.** 공정은 재료와 같은 부류다 — *가진 것*이고, *닿을 수 있는
범위를 제한한다.* 목표(B)도 정체(A)도 아니다. 그래서 Phase C 의 이름이
"재료" 에서 **"재료와 공정"** 이 되었다.

**무엇을 묻는지는 계산된다.** 제형마다 core 축이 어떤 파라미터에 걸려 있는지를
R-1 로 타고 구한다(`process.fields()`). 관능 질문을 하드코딩하지 않은 것과 같은
이유다.

| 제형 | 칸 | 묻는 것 |
|---|---|---|
| 아이스크림 | **5** | 동결(장비·시간) · 공기 넣기 · 믹스 준비 · 보관 |
| O/W 소스 · 음료 | 3 | 가열 · 유화·균질(장비·세기) |
| 현탁액 · 발효 핫소스 | 3 | 가열 · 분쇄(장비·굵기) |
| 쌀음료 | 1 | 가열 |

**1 단계는 기록까지다.** 전부 자유 서술이고 값을 해석하지 않는다. 지문(sha1
12자)만 만들어 **같은 지문끼리만 함께 학습**한다. 조종 수단으로 쓰는 것은
PROCESS 가 붙는 2 단계다.

**다른 단계에 미치는 영향**

- `C4 GAPFILL` — 빈 곳이 재료뿐 아니라 공정일 수 있다
- `D0 FEASIBILITY` — 규모로 못 가는 목표를 가려낸다. 되돌아갈 곳이 넷이 된다
- `E1 RECORD` — 실제로 쓴 공정을 받아 선언과 다르면 블록을 나눈다
- `D4 DOE` — **공정을 고정하면 실험이 줄어든다.** "적을수록 좋다" 와 같은 방향이다

## 5. 제품 사전

**위치** `ontology_v2/layers/layerS3_products.yaml` (새 파일). 앱이 직접 읽는다 —
정본 로더의 glob(`layerC2_*`, `layerM_cards_*`, `layerL_*`, `layerS2_*`)에 안 걸린다.

**성질** 새 주장을 담지 않는다. 이미 있는 profile id 와 term id 를 가리키는
**색인**이라 불변식과 충돌하지 않는다.

```yaml
- id: PROD.hot_sauce_fermented
  ko: 발효 핫소스
  aliases: [핫소스, 매운소스, 고추장소스]
  profile: suspension
  identity_axes: [L.ch.pungent_hot, L.ch.heat_linger,
                  L.ar.dried_red_chili, L.ar.soy_fermented_jang]
  typical_ingredients: [ING.gochugaru_coarse, ING.gochujang, ING.vinegar_brewed]
```

**덤으로 뿌리가 뽑힌다.** 현탁액 카드가 하드코딩한 "default product: fermented
hot sauce" 가 이 항목으로 옮겨 간다. 제형은 다시 일반적인 것이 되고 제품이
정체성을 진다.

**작업 방식** 30개 내외 초안 → `draft_review.xlsx` 방식 검토표 → 판정 반영.
특히 확인받을 것: 마요네즈·드레싱이 `sauce_ow` 인지, 살사·핫소스가
`suspension` 인지.

## 6. A3 `DISAMBIGUATE`

"소스" 는 `sauce_ow`(에멀전)와 `suspension`(현탁) 둘 다다. 제품 사전에 있는 말
(마요네즈, 살사)은 사전이 끊는다. 일반어면 **한 가지만 되묻는다**:

> "기름이 들어가나요, 아니면 건더기가 씹히나요?"

이 한 질문이 O/W 와 현탁을 정확히 가른다. 두 개 이상 묻지 않는다.

## 7. C3 `ENROLL` — 미등록 재료

INGREDIENT 헤더가 이 길을 이미 열어 뒀다:

    2-TIER: generic effects live on FUNCTION TAGS
            (prior backbone + enables new-ingredient generalization via descriptors)

새 재료에 필요한 것은 **이름 + 기능군** 뿐이다. 그 순간 태그의 사전 효과를
물려받아 모형에 들어간다. 전문가 검증은 override 를 붙이는 일이지 사용자를
막을 이유가 아니다.

**파일** `layerC2_ext_provisional.yaml` — append-only (불변식 3)

```yaml
- id: ING.<slug>
  ko: <사용자가 적은 이름>
  function_tags: [FT.*]        # 한글 이름 붙은 기능군 24개 중에서
  status: provisional
  confidence: low
  added_at: <날짜>
  review: pending
```

**화면** 제안 결과에 "아직 검증 전인 재료" 표시. 전문가 화면에 검토 대기열
(`review_drafts.py` 패턴 재사용).

## 8. C4 `GAPFILL`

부품은 이미 있다 — `default_palette()` 의 축별 대표 선택과 STRUCTURE 의
`required_functions`. 사용자가 댄 재료 집합을 K 라 할 때 빈 곳은 둘이다.

1. **제형이 요구하는 기능군 중 K 가 못 채운 것**
   → "O/W 소스인데 유화제가 없습니다 → 난황"
2. **core 축 중 K 로 못 움직이는 것**
   → "걸쭉함을 조절할 재료가 없습니다 → 잔탄검"

각각 이유와 함께 제안하고 수락/거절을 받는다. 기능군 아코디언은 접어서 남긴다.

## 9. 착수 순서

"API 키 없이 갈 수 있는 데까지 간다" 를 전제로 다시 잡았다.

| 순서 | 할 일 | 단계 | API | 상태 |
|---|---|---|---|---|
| 1 | 질문 선택 정책 + 정체성 축 칩 | `B1`, `A4` 일부 | 없음 | **완료** 2026-09-02 (미커밋) |
| 1.5 | 현탁액에서 제품을 떼어낸다 | — | 없음 | **완료** 2026-09-02 |
| 2 | 제품 사전 초안 30 + 검토표 | `A2`·`A3` 의 전제 | 없음 | |
| 3 | 재료 검색 · 잠정 등록 · 빈 곳 제안 | `C1`~`C5` | 없음 | |
| 4 | 서술형 파싱 + 참조 세 역할 | `A1`~`A4` | 필요 | |

**1번이 앞으로 왔던 이유.** 전에는 제품 사전이 1번이었는데, 사용자의 불만 자체는
`default_goal` 을 읽는 것만으로 풀린다. 정체성 축을 ② 에서 빼내 "지울 수 있는
칩" 으로 올리면 끝이고, 제품 사전은 그 칩의 **좋은 기본값**을 주는 일이라 뒤에
와도 된다.

**1.5 가 새로 생긴 이유.** 4.6 절의 발견 때문이다. `selfcheck_v2` 가 지금 2건
실패하고 둘 다 현탁액이다. 할 일은 셋:

1. `layerM_cards_suspension_hotsauce.yaml` 을 제품 단위 파일(F7)로 신설 —
   `meta.product: 발효 핫소스`, 정체성 축 3개(매운맛 · 건고추 향 · 장 발효 향)
2. `layerM_cards_suspension.yaml` 과 STRUCTURE 의 `relevant_attributes` 에서 그
   4개를 뺀다. `감칠맛` 은 `target` → `maintain` 으로 강등
3. `suspension` 의 meta 에서 `- default product: fermented hot sauce` 삭제.
   대신 STRUCTURE 에 칸 수만 남긴다 — 향 슬롯 2개

2번과 순서를 바꿔도 되지만, 1.5 를 먼저 하면 제품 사전의 첫 항목
(`PROD.hot_sauce_fermented`)이 그 파일을 가리키기만 하면 되어 일이 줄어든다.

## 10. 보류

### ±3 척도의 의미 — **별도 채팅에서**

판단 근거: 이 주제는 모델 내부 정의(`RANGE_TO_SD`=4.0 가정, reliability→σ
0.5/1.0/1.8, `diff_7` 과 `jar_5` 혼재)와 관능과학 문헌을 동시에 파야 하고,
결론이 온톨로지 카드(`ko.anchors`)와 엔진 양쪽에 닿는다. 여기서 하면 UX 작업이
멈추고, 산출물이 문서 하나라 옮겨 오기도 쉽다.

넘길 것:
- 지금 `ko.anchors` 는 "기준보다 뚜렷하게 더 달다" 같은 **방향과 어조**만 있고
  **크기**가 없다
- `RANGE_TO_SD = 4.0` — 작업 범위 폭을 4 SD 로 본다는 가정. 근거 미검증
- reliability → σ: high 0.5 / medium 1.0 / low 1.8
- 카드가 `diff_7`(−3…+3)과 `jar_5`(JAR) 둘로 갈려 있는데 화면은 하나로 묻는다
- 4장의 `anchors` 는 −3/0/+3 이 아니라 강도 기준점(intensity/reference) 목록이다

### DoE / 실험 횟수 — 다른 것 끝낸 뒤

**전제: 적을수록 좋다.** 첫 배합은 하나여도 좋다. 목적에 따라 여러 개일 수
있지만 늘리는 쪽이 아니라 **최소화하는 쪽이 목적**이다. 품질·난이도에 따라
늘어나더라도 그 방향을 잊지 말 것.

계산 근거는 이미 있다: 자유변수 q = p−1, warmloop 의 `eff_directions`
(쌀음료는 15개 중 11개 방향만 탐색됨), reliability→σ, 스펙 5.7 의 5~20회 지침.
